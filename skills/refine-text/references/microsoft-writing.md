# Microsoft Writing Style

Use this profile when the user requests Microsoft style or the document clearly follows Microsoft product-writing conventions. It is best suited to product documentation, UI text, help content, procedures, error messages, websites, and technology-focused communication.

## Authorities and Precedence

- [Microsoft Writing Style Guide](https://learn.microsoft.com/en-us/style-guide/welcome/)
- [Microsoft's brand voice](https://learn.microsoft.com/en-us/style-guide/brand-voice-above-all-simple-human)
- [Procedures and instructions](https://learn.microsoft.com/en-us/style-guide/procedures-instructions/)

A supplied product, team, localization, terminology, or UI guide outranks this general profile. Preserve established product language when it differs from a generic Microsoft preference.

## Product Fidelity

- Preserve product and feature names, trademarks, UI labels, commands, code, paths, keyboard shortcuts, settings, values, outputs, error text, and technical terms.
- Do not change product behavior, requirements, permissions, supported platforms, defaults, limitations, security consequences, or sequence dependencies.
- Never invent a feature, control, menu path, cause, solution, workaround, result, or customer promise.
- Do not claim that a procedure was tested or an interface was inspected unless the source establishes it.

## Voice and Tone

- Be warm and relaxed, crisp and clear, and ready to help, while adapting tone to the user's situation.
- Lead with the key takeaway, action, choice, or next step.
- Use familiar, conversational words and contractions when they fit the document and audience.
- Focus on what the reader can do. Do not add cheerfulness, empathy, urgency, reassurance, or marketing language unsupported by the source.
- Avoid blame, condescension, jargon, unnecessary acronyms, idioms, and culturally specific references.
- Keep enough information for the reader to act confidently, but do not overload UI or help text with background.

## UI Text and Error Messages

- Preserve exact control names and interface labels.
- Use concise, input-neutral verbs when accurate, such as `select`, `open`, `close`, `enter`, or `clear`.
- Make button labels and commands describe the action when label editing is in scope. Do not rename an actual product control.
- For an error message, state what happened, the known reason only when the source establishes it, and the next available action.
- Never blame the user or promise that a step will resolve the problem unless the source supports that result.
- Keep required warnings, privacy language, permissions, and security consequences visible and precise.

## Procedures and Help

- Use a task-oriented heading and begin with the action or outcome the reader needs.
- Remove an introduction that merely repeats the heading.
- Use numbered steps for a sequence and parallel imperative verbs when formatting changes are in scope.
- Identify where an action occurs when omission could confuse the reader.
- Keep prerequisites, conditions, notes, and alternatives next to the step they govern.
- Do not document a procedure when the source indicates that the interface itself already supplies all necessary guidance.
- Preserve alternative input methods and accessibility information already present.

## Global and Accessible Writing

- Prefer plain, literal language that is easy to scan, translate, and localize.
- Avoid directional or sensory instructions as the only way to identify a control.
- Preserve meaningful headings, lists, tables, links, alt text, labels, and reading order.
- Do not introduce an input-method assumption, cultural reference, or accessibility claim absent from the source.

Do not claim complete Microsoft-style compliance unless the applicable product guidance and current style-guide sections are available.
