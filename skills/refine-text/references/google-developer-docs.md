# Google Developer Documentation

Use this profile for developer-facing documentation when the user requests Google style or the document clearly adopts the Google Developer Documentation Style Guide. It applies to API guides, tutorials, conceptual documentation, procedures, and technical reference prose. It is not Google's corporate brand guide or a code-style guide.

## Authorities and Precedence

- [Google Developer Documentation Style Guide](https://developers.google.com/style)
- [Highlights](https://developers.google.com/style/highlights)
- [Voice and tone](https://developers.google.com/style/tone)

Follow project- or product-specific guidance first, this profile second, and the shared grammar guidance third. Preserve a consistent project convention when it differs from a default here and still serves the reader.

## Technical Fidelity

- Preserve code blocks, inline code, API and product names, commands, flags, filenames, paths, configuration keys, UI labels, example values, outputs, version numbers, units, and error text.
- Do not change described behavior, prerequisites, permissions, defaults, limits, sequence dependencies, security implications, or compatibility claims.
- Never invent a code sample, command result, prerequisite, test result, link target, feature, or troubleshooting outcome.
- Do not claim that code was run, a procedure was tested, or a feature works unless the source establishes it.
- Keep distinctions among conceptual explanation, instruction, reference, note, warning, and example.

## Voice and Language

- Address the reader as `you` when direct address fits. Avoid using `we` when the actual actor can be named.
- Prefer active voice and present tense while preserving meaningful conditions, future behavior, and modality.
- Sound conversational, friendly, respectful, and technically competent without slang, hype, cuteness, or forced humor.
- Write for a global audience. Prefer literal, culturally neutral language and avoid unexplained idioms, pop-culture references, and unnecessary figurative language.
- Do not call a task `easy`, `simple`, `quick`, or `obvious`. Those judgments do not help a reader who is blocked.
- Use one precise term for each concept and match the product or API's authoritative terminology.

## Structure and Procedures

- State the reader's goal and necessary context before details that do not affect the task.
- Put a condition before the instruction it governs.
- Use descriptive, sentence-case headings that help readers locate tasks or concepts.
- Use numbered lists for ordered procedures and bullets for unordered items when formatting changes are in scope.
- Write procedure steps as direct actions with parallel grammatical structure.
- Include prerequisites, locations, and expected results only when the source supplies them and the reader needs them.
- Use descriptive link text rather than generic labels such as `click here` when link editing is in scope. Never invent or alter a link target.
- Keep notes and warnings close to the step or claim they qualify; do not promote ordinary information into a warning.

## Accessibility and Formatting

- Preserve semantic headings, list structure, alt text, tables, anchors, and code formatting.
- Do not rely only on color, direction, position, or sensory language to identify an interface element.
- Preserve exact UI labels. Use an input-neutral action verb when it accurately describes the source interaction.
- Do not reformat code-related text or UI elements unless the request includes formatting and the target format is known.

Do not claim complete Google-style compliance unless the applicable project guidance and current style-guide sections are available.
